# Security review - BuddyPress Member Reviews 3.8.3

Scope: full diff v3.8.2..3.8.3 plus every AJAX, admin-post and admin_init handler in the plugin (no REST routes in Free; Pro's REST API reads and writes the same review posts, so it was walked in the same run, see `buddypress-member-review-pro/audit/security/1.0.1.md`). Method: code read of each handler and each `$wpdb` call site, then the in-process authorisation matrix and an HTTP pass on a throwaway Docker stack (WP 7.1, BuddyPress 14.5.6, Free 3.8.3 built zip + Pro 1.0.1 built zip, all BuddyPress components on). Actors: guest, a second same-role member, the review author, the reviewed member, an Editor and an Administrator, each with their own nonce.

Reproduce: `g2-matrix.php` (in-process, `wp eval-file`, run once per review mode) and `g2-http.sh` (guest and subscriber over HTTP) in this folder.

## Findings fixed in this release

| Severity | Where | Attacker story | Fix |
|---|---|---|---|
| Low | `includes/bupr-ajax.php` `bupr_flag_review` | Any logged-in member could POST a report against a pending or auto-hidden review by guessing its sequential ID. It wrote report data onto a review nobody else can see and told the reporter the ID exists. | Only published member reviews can be reported; anything else answers "Review not found". |

The matrix showed this as a failing cell before the fix and passing after it.

## Findings open, not release-blocking

| Severity | Where | Story | Note |
|---|---|---|---|
| Low | Profile Reviews tab and single review view (`includes/templates/bupr-reviews-tab-template.php`, `bupr-single-review-template.php`) | A review an administrator has password-protected in wp-admin is still printed in full to everyone, because these queries never exclude password-protected posts. No member or visitor can set a post password; it needs an administrator's deliberate action. | Same class Pro's REST list already refuses. Recommend a card: skip `post_password_required()` reviews on both surfaces. |
| Info | `bupr_approve_review` | An Editor or Administrator can approve a pending Group Review through the Member Reviews approve action. | Moderator-only (`edit_others_posts`), the action the Group Reviews screens expect. Accepted. |

## G1 mechanical sweep (own code, baseline v3.8.2)

No CRITICAL pattern. Against v3.8.2 the sweep adds four `sql-direct-interpolated` hits and one more `no-abspath-guard` file; nothing else changed. Every one is triaged below.

## Scanner-visible but safe

- `sql-direct-interpolated` (4): the 3.8.3 additions interpolate only `$wpdb->postmeta` / `$wpdb->usermeta` / `$wpdb->posts` table names, the fixed constants `bupr_owner_reply_date`, `bupr_auto_hidden_date`, `bupr_flags` (`bupr_run_utc_migration`, `bupr_maybe_run_utc_migration`, the repair counts) and a `NOT EXISTS` fragment built from two literal key lists (`bupr_mode_sql_exclusion()`, `$alias` is the literal `p`). All 13 `$wpdb` query call sites in own code were opened; every request-derived value goes through `prepare()` (`%d` or `%s`) or `absint()`. The widget's `ORDER BY` is picked from a two-entry allowlist (`includes/widgets/display-review.php`).
- `nonce-only-auth` (1): `bupr_approve_review` checks the nonce and `edit_others_posts`; the sweep only sees `check_ajax_referer`.
- `extract-call` (1): `bupr_get_template()` extracts an `$args` array that only internal callers fill (`review_id`), never request data.
- `no-abspath-guard`: `uninstall.php` guards with `WP_UNINSTALL_PLUGIN`; the dev scripts under `audit/` and `bin/` are not in the release zip.
- No `wp_ajax_nopriv_` handler anywhere; guests reach none of the 13 AJAX actions of the pair (Free 6, Pro 7) (HTTP 400 on every one).
- Migrations on `admin_init` (`bupr_maybe_run_utc_migration`, `bupr_repair_slug_criteria`, `bupr_maybe_run_meta_repair_migration`) read no request data.

## G2 authorisation matrix

Every AJAX action, admin-post action and the Pro REST and admin_action routes, per actor, with a valid nonce and a schema-valid payload. Two runs (Star Ratings and Endorsements mode, because endorsement handlers only exist in that mode); each cell passes in at least one run except the one noted. Includes the write verbs, the "still unchanged" read-back after a refused write, wrong-role, wrong-nonce, group-review and draft/password cases.

- Ratings run: 204 of 211 cells pass; Endorsements run: 207 of 211. The non-passing cells are the endorsement preconditions in Ratings mode and the criteria handlers in Endorsements mode (handlers not registered in that mode, asserted explicitly so a missing hook cannot read as a pass), plus the item below.
- Not a leak: a plain-Subscriber author cannot read their own pending review through the Pro REST API (404; `can_read_review()` uses `edit_post`). Their PUT works. Recorded as a Pro functional gap.
- HTTP pass: 28 of 28. Guests blocked on all 13 AJAX actions, a forged `bupr_current_user` is ignored (author is the session user), self-review refused, out-of-range ratings dropped, Subscriber gets 403 on every plugin admin screen and on `options.php`, guests get 400 on admin-post.
- Probes are mutation-proven: the flag-on-draft cell and Pro's password-protected REST cell went red against the unfixed code before the fixes.

## G3 reviewed diff

`git diff v3.8.2..HEAD` read for request handling, output escaping, SQL and capabilities: the star-font and class renames are markup only; the email defaults moved to one helper (`bupr_email_setting()`, output escaped at send); the UTC migration and slug repair touch only owned meta keys; the top-members cache moved to the object cache keyed on a last-changed token (the key holds one of two literal meta keys, filterable only by a developer hook, and the limit); the shortcode and widget limits are cast to int and floored. No finding beyond the table above. A whole-plugin pass was done in the 3.8.1 review; this release re-walked every handler listed above.
